# 源码地图 / Source map

源包是解包后的安卓 APK（`com.frog.offline`，v1.0.20-offline），一个 Egret H5 游戏
套在极薄的 WebView 壳里。这份文档记录**哪些文件被用到、哪些被丢弃、以及为什么**，
避免以后有人重新翻一遍。

## 1. 源包全景

| 路径 | 内容 | 本项目怎么处理 |
|---|---|---|
| `AndroidManifest.xml` (2.4KB) | 安卓清单 | **丢弃**（原生壳） |
| `classes.dex` (23.9KB) | 安卓壳的字节码，只有一个 WebView Activity | **丢弃** |
| `resources.arsc` (784B) | 安卓资源表 | **丢弃** |
| `res/`、`META-INF/` | 安卓资源与签名 | **丢弃** |
| `assets/game/` | H5 游戏本体 | **全部静态托管** |
| `resource/China/` | 中国之旅的美术与配置 | **全部静态托管** |
| `resource/ejoysdk_lua/` | 安卓 SDK 的 lua 脚本，仅原生运行时使用 | **丢弃** |

`scripts/fetch-source.js` 只拷 `assets/game/` 与 `resource/China/`，并在结束时**校验**
`vendor/` 里没有出现 `AndroidManifest.xml` / `classes.dex` / `resources.arsc` /
`META-INF`——这是验收项之一，所以由脚本自己证明，而不是靠人记得检查。

拷贝规模：game 26 个文件 6.8MB，resource 3863 个文件 257.6MB。

## 3. `__offline-engine.js` 内部结构

文件头写着 `AUTO-GENERATED by work/tools/bundle_engine.py`。它是一个手写的
CommonJS 打包器：`define(name, fn)` 注册模块，`req(name)` 解析，最后
`global.FrogEngine = req('./index')`，整个 IIFE 以 **`window` 作为 `global` 传入**——

```js
(function (global) { ... })(window);
```

这一点决定了宿主怎么写（见 §5）。模块清单（行号是文件内的）：

| 行 | 模块 | 内容 |
|---:|---|---|
| 48 | `fs` | localStorage 版文件系统桩 |
| 114 | `path` | `join`/`dirname`/`basename` |
| 124 | `./protocol` | 243 条协议定义（`needResponse` + 参数名） |
| 1375 | `./data/gamedata.json` | 从客户端 DB 抽出的 60 张表 + 411 条 item |
| 68021 | `./data/define.json` | **原版服务端调参表**：85 个 scalar + maps |
| 68431 | `./data/picture-layers.json` | 明信片合成配方（重建，非原版数据） |
| 68435 | `./data/travel.json` | 目的地系统 6 张表（Area/Node/NodeConnect/NodeEdge/NodeGoal/NodeItem） |
| 68442 | `./index` | **引擎主体**（约 8700 行）：状态、tick、所有 handler、GM 指令台 |

导出的 API（`module.exports = { createEngine, canon, toWire, nowSec, defaultState, makeClovers, CLOVER_SLOTS }`）：

```js
const engine = FrogEngine.createEngine({ savePath: 'save.json', verbose: true });
engine.state          // 可读的完整存档
engine.dispatch(cmd, data)  // -> { reply?, handled, pushes: [{cmd, data}] }
engine.tick()               // -> [ {cmd, data} ]  时间驱动的推送
engine.save() / exportSave() / importSave(obj) / saveInfo() / forceSaveOverwrite()
engine.unknownReport()      // 未知指令计数（勘察用）
```

### 3.1 两个关键机制

**收消息入口**：`dispatch(cmdWire, data)`。`canon()` 把 wire 名的第一个 `.` 换成 `_`
（`client.load_role` → `client_load_role`），handler 表按**下划线名**索引；
`toWire()` 做反向转换，只换第一个下划线。返回值里 `pushes` 是本条指令引发的
服务端主动消息。

**主动推送**：handler 通过闭包里的 `ctx.push(name, data)` 投递，`dispatch` 和 `tick`
各自构造一个 `ctx`，所以推送要么跟着回包返回、要么从 `tick` 返回。引擎自己不会
发网络消息——**这就是为什么宿主只需要一个循环把它返回的东西 fan-out 出去**。

### 3.2 存档层

引擎通过 `fs` 桩读写，键的规则：

```
主存档          'frog.offline.save'
备份/临时/损坏槽 'frog.offline.save::save.json.bak' / '::save.json.tmp' / '::save.json.corrupt-<ts>'
```

浏览器里这些是 localStorage 的键；本项目把每个键落成 `data/save/<key>.json`，
键名本身已经满足文件名约束（`fileForKey()` 只对 `.corrupt-<ts>` 之类的字符做兜底替换）。

`save()` 的写入是"先写 tmp 再 rename"，并且先备份主档；读取时按
**主存档 → 备份 → native 镜像** 三级恢复，并在 `state.__saveReport` 里报告
`restoredFrom`。宿主不额外包一层，避免出现第二套真相（见 `docs/decisions.md`）。

### 3.3 调参开关（FROG_CONFIG）

```js
var process = { env: (global.FROG_CONFIG && global.FROG_CONFIG.env) || {} };
```

即：在沙箱里注入 `FROG_CONFIG.env` 就等于给引擎设置了 `process.env`。
共 30 个可覆盖项，最有影响的是：

| 变量 | 默认（离线） | `FROG_FAITHFUL=1` | 含义 |
|---|---|---|---|
| `FROG_FAITHFUL` | — | `1`（本项目默认） | 用 define.json 的原版真实时长 |
| `FROG_TRAVEL_MIN` / `_MAX` | 12 / 40 分钟 | 3600 / 21600 秒 | 单次旅行时长 |
| `FROG_IDLE_MIN` / `_MAX` | 2 / 6 分钟 | 60 / 180 秒 | 回家后再次出门的间隔 |
| `FROG_WAIT_MIN` / `_MAX` | 3 / 8 分钟 | 60 / 180 秒 | 没备行李时的重试间隔 |
| `FROG_DRIFT_MIN` / `_MAX` | 10 / 20 分钟（默认覆盖，见 D75） | 同左 | 放浪（没带便当）回家时长 |
| `FROG_GUEST_ROLL` / `_CHANCE` | 60 秒 / 35% | 1800 秒 / 10% | 邻居访客掷骰 |
| `FROG_VISITOR_*` | 由本项目决定 | — | 串门访客节奏（原版在服务端，无据可依） |
| `FROG_LOTTERY_*`、`FROG_DRAWING_*`、`FROG_CRAFT_SEC`、`FROG_WISH_*`、`FROG_CAPSULE_*` | 见 `/admin` 页面 | — | 其余活动节奏 |

其余未列入的常量（如 `FOUR_LEAF_CHANCE`、掉落权重）**不提供覆盖**，因为它们
属于玩法数值，改了就不是原版了。

### 3.4 与原版不同的地方（引擎作者已标注）

引擎注释里明确区分了「恢复的原版数值」和「自设计」两类：

- **恢复的**：便当 HP→旅行时长、`Define` 里的装备/访客/奖励权重、旅行地图
  （6 张表 + Item.effects 全是原版服务端表）。
- **自设计的**（引擎注释标了 `【自设计】`）：工作中的制作配方与时长、
  串门访客节奏、许愿池节奏、明信片合成配方（`picture-layers.json` 是**重建**，
  靠渲染结果目视校验，不是原版数据）。

本项目不改这些数值，只在 `docs/decisions.md` 里记录"以引擎为准"。

## 5. 宿主与 bundle 的契约（踩过的坑）

bundle 以 `window` 为 `global`，所以 `node:vm` 沙箱里必须成对提供：

```js
sandbox.window = sandbox;      // 否则 FrogEngine 挂在空对象上
sandbox.global = sandbox;
sandbox.self   = sandbox;
sandbox.localStorage = <磁盘适配器>;
sandbox.FROG_CONFIG  = { env: {...} };
sandbox.process = ...          // bundle 自己定义了局部 process，无需注入
```

`__dirname` 由 bundle 自己声明为 `''`，`fs`/`path` 是它自带的桩，所以**不需要**
真的 `node:fs`——这一点容易误判：文件里 `require('fs')` 命中的是桩，不是 Node 内置。

## 6. 客户端（`js/main.min.js`）里与本项目相关的三处

1. **协议表** `ProtocolList.protocolList`（第 375283 字符处起）：243 条，形如
   `clover_harvest: [["clover_id"], true]`——`[参数名数组, needResponse]`。
   这是 API 层映射表的依据。
2. **网络层** `core.SocketManage`：`send(cmd, action, ...args)` 序列化信封
   `{session?, timestamp, cmd, data}`；`AnalysisProtocol(str)` 按 `cmd` 是否为空
   区分"回包"与"推送"，按 `session` 把回包派发给对应回调。
   **`cmd` 只把第一个下划线换成点**，所以 wire 名可能是 `client.load_role`，
   也可能是 `client_load_role`——引擎的 `canon()` 两者都吃。
3. **登录时序** `NetworkControl.totalEvents`：
   `ConnectionSucceed` →（channel=Test）`hall_gen_token(userName)` →
   回包 `getToken` → `hall_login(token)` → 回包 `loginComplete` →
   `hall_enter_game`。本项目 bot 客户端复刻的就是这条链。

## 7. 无头调试设施（探针）

`__probe.js` 支持这些查询参数，本项目**全部保留**（原文件不改）：

| 参数 | 作用 |
|---|---|
| `?log=1` | 把 `console.*` 与未捕获错误 POST 到 `/__log`（内存副本恒在 `window.__probeLog`） |
| `?tap=x,y[,x,y...]` | 合成点击（无头环境没有指针） |
| `?tapdelay=ms` | 何时开始点击，默认 12000 |
| `?dumptree=秒` | 转储 Egret 显示树 + 季节性资源状态 |
| `?transport=ws` | **跳过页内引擎回环**，走真实 WebSocket——即本项目的 Route A |
| `?showGM=1` | 打开客户端自带的 GM 面板 |

`?tap` 只用于 E2E 冒烟；skills 的 REST 动作走服务端 bot，不做 UI 自动化。
